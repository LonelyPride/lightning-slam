## 2. 2026-10-01 逐条记录

### 2.1 地图歪、地面叠成好几层（第 1 批，18:36 构建）

**现象**：离线建完图，保存的点云 z 向跨度从 25.7 m 涨到 69.5 m；同一片地面在不同帧里被放到不同高度，看着像"多层壳"；地图地面整体是斜的。

**大白话根因**：关键帧里存的点云是"**雷达自己坐标系**"的点（本平台竖装：x=左、y=上、z=前），
而关键帧的位姿是"**IMU 系**"的位姿。拼图时把这两个直接相乘，等于**假装"雷达和 IMU 装在一起、一点偏差都没有"**，
把真实的"雷达→IMU 外参"整个漏掉了（本平台是一个 90° 航向 + 4 mm 平移）。
于是每个关键帧都带着歪 90° 的姿态贴进地图，车一俯仰，同一片地面就被摆到不一致的高度 → 叠层壳。

**改了什么**

| 文件 | 改动（人话） |
| --- | --- |
| `src/core/lio/laser_mapping.cc` | 拼图函数 `GetGlobalMap()`：变换点云前先把外参补上（`vehicle_frame::ToLidarPose(...)`） |
| `src/common/vehicle_frame.h` | **新增**（纯头文件）：放"这个系换那个系"的一堆小工具，所以不用改 CMake |

**怎么验证的**：不只"看着顺眼"——用独立重建的点云做逐点交叉比对、地面平面度、叠层结构、目视对比，四条判据一起看。
改后同一 bag 重跑，`global.pcd` 三次运行**逐点最大差 = 0.000e+00 m**（证明"改动没扰动本来就对的结果"）。
另外顺手确定了一条经验：**PCD 不要只看 md5**（点结构里有未初始化的对齐填充字节，压缩后字节数会随机波动），要比点坐标。
→ 细节见 `doc/global_map_extrinsic_fix_report.md` 第 1~9 章。

### 2.2 同一个病根的另外几处（第 2 批，19:20 构建）

**现象**：建图看着好了，但定位还是不行；栅格图 `map.pgm` 明显错乱（而且两版 md5 竟然一模一样，说明它根本没走上面那条修好的通路）。

**大白话根因**：同一个病根「**把雷达系的东西当 IMU 系的用**」在另外 4 处都有，只是它们输入输出用同一套错坐标系，误差被"自洽"地掩盖了，只会**悄悄变差**：

### 2.3 在线定位"完全不可用"（第 3 批，20:40 构建）

**现象**：同一条 bag 先建图、再用它定位 → 初始化分值 **0.679**（门槛是 1.8）却被当成"初始化成功"，
随后分值塌到 0.07~0.14、位姿在地图原点附近乱跳；**同一张地图用离线入口却完全正常**。用户当时怀疑"还是坐标系问题"——判断正确。

**大白话根因**（在线入口独有的两个坑，任一都足以让定位不可用）

1. 在线入口无条件执行 `SetInitPose(SE3())`，把**单位阵**当成"雷达在地图下的位姿"塞进去 —— 等于告诉程序"车就在地图原点、还摆得正正的"；
2. 初始化那段代码的分值门槛写成了 `if/else` **两个分支都置"成功"**（恒真），门槛形同虚设：
   这个错初值被**无条件接受**，`loc_inited_` 变成 true 之后，① 靠地图功能点 `start` 初始化的回退分支**永远不会被执行**，
   ② 重试逻辑全在"还没初始化"的分支里 → **再没有第二次机会**。

**改了什么**

| 文件 | 改动（人话） |
| --- | --- |
| `src/app/run_loc_online.cc` | 删掉那句无条件注入；默认改调新增的 `LocSystem::Start()`（**不注入任何外部位姿**，跟离线入口一致，靠功能点 `start` 初始化）；新增**可选**命令行 `--init_pose "x,y,z,qx,qy,qz,qw"`（语义 = 雷达系在地图下的位姿） |
| `src/core/system/loc_system.{h,cc}` | 新增 `Start()`；`SetInitPose()` 的注释写清"必须传雷达系在地图下的位姿，别传车辆/IMU 的" |
| `src/core/localization/lidar_loc/lidar_loc.cc` | 初始化分支**真正判**比分门槛（不够就打 `init confidence too low ...` 并拒绝）；跟踪阶段的逻辑一点不动 |

**怎么验证的**：用用户的原始命令 + 原始 bag + 原始地图，全程 238 s 跑通，日志变成 `start loc without external init pose, use map functional point 'start' instead`。
→ 细节见 `doc/global_map_extrinsic_fix_report.md` 第 11 章。

### 2.5 把栅格地图用话题发出去（新功能，23:28 构建）

**为什么要**：下游规划/控制要地图，别让它们自己去读文件、各自去解析 pgm/yaml。

**改了什么（人话）**：定位进程里开一个线程，启动时把 `map.pgm` + `map.yaml` 读进来、转成
`nav_msgs/OccupancyGrid`，按周期**持续发布**。配置项 `system.publish_map.*` 全是**可选键**（缺键、甚至整段删掉都能跑）。

### 2.9 方案A / 方案A+：姿态输出统一到"车辆系"（10-01 下午，其实是最早的一批）

> 说明：这一批时间上最早（`vehicle_frame.h` 是 10-01 17:27 建/改的），写在 §2 末尾只是**为了不打乱前面已写好的编号**。

**现象**：UI/日志里车像是"绕 y 轴立起来 90°、要上天"；用 roll/pitch/yaw 读姿态时 pitch 恒在 ±90° 附近，
真正的拐弯跑到 roll 上，±180° 附近乱跳。

**大白话根因**（滤波器、地图、世界系本身都是对的，**别去动它们**）：

1. 问题只在"把 **IMU 的姿态直接当成车体的姿态**输出"。本平台 IMU 是**竖装**：IMU 系 `x=下, y=左, z=前`；
   车辆系 `x=前, y=左, z=上`，两者差一个固定的 `R_y(+90°)`。静止起步时车体姿态恰好就是这个量，所以画出来"x 轴指地"= 立起来了；
2. 旧代码用 `SO3::angleX/angleY/angleZ` 读姿态 —— 它们**不是真正的 RPY**（是 2×2 子块的 SVD log），
   竖装时退化：实测静止时旧 `angleZ` 读到 −162°，而真实朝向只有几度。

**改了什么**：只在"输出/显示边界"换算，**不动滤波器**：`T_w_vehicle = T_w_body * Mᵀ`（M = 车辆系相对 IMU 系的安装旋转），
姿态角改用标准 ZYX 欧拉角。涉及 LIO 日志、LIO→UI、UI（新增 `UpdateBodyPose()`）、定位→TF、定位→UI，
换算工具都收在新增的 `src/common/vehicle_frame.h`。

**方案A+（同一天接着改的）**：安装旋转**不再写死**，改成 yaml 可配（`common.vehicle_imu_mount` = `auto/identity/x_down/x_up`、
`vehicle_imu_forward_axis`、`vehicle_imu_R`）；`auto` = 用 IMU 静止初始化测到的**重力**自动定"上"，任意倾斜安装都能自适应。
为什么必须改：本平台"标称竖装"与真实"上"实测差 **11.25°**，写死会让车永远带一个 11° 的歪角。

**对外行为变化（要通知下游）**：`map→base_link` 从"雷达系位姿"变成"**真正的车辆系姿态**"，
按老约定解析的下游需要同步（本平台两者差约 90°）。若安装旋转没配（默认单位阵），行为与改前一致。

**怎么验证的**：整包编译 0 error；换算工具单元测试全过（静止、±179° 转向、俯仰/侧倾、定位端换算、点云落图一致性）；
离线跑 `run_slam_offline` 308 帧：直线段 `rpy ≈ [0,0,ψ]`，把世界系速度投影到车辆系后**前进分量占绝对主导**
（≈0.45 m/s，左/上分量 < 0.2 m/s）⇒ 坐标系约定确实一致了。→ 细节见 `doc/airy96_config_guide.md` 第 11 节（含 11.1 方案A+）。

### 3.2 方案C 第 2/3 次加固：判据 3 道 → 5 道（上午）

**为什么要加固**：方案C 的判据看的是加计读数，而加计测的是**比力（重力 + 平动加速度）**，不是重力。
实测最吓人的一组数字：**真静止时自检读数 0.26°，而同一次运行里车加速/过坎的一瞬间读到 15.58°（差 60 倍）**。

**加的两道（前面 3 道是幅值、角速度、方向散布）**

| # | 新判据 | 挡住什么 |
| --- | --- | --- |
| ④ | **平动加速度**（用 `LIO 世界系速度差分`来估，**与加计无关**） | **恒定的加/减速**（前 3 道全瞎） |

### 3.3 方案C 第 4 次修复：三处"判据/数值"级改动（下午）

> 本轮**没有新增任何观测/模块**，只改门限、改数值、加日志与自检，所以改动面很小但都是直的。

**① 行驶中的"竖直锚"（本平台 roll 漂 / z 漂的真正修复）**
- 实测证据：行驶中重力观测被**恒跳过**（方向散布门限 3° 一撞就穿，实测 3.20°），
  而滤波器有个特性：这次更新判定无效时会**整体回滚**（日志表现为 `d_rot = 0 deg`）⇒ **行驶中姿态完全没有竖直约束**，roll 单边一路涨。
- 改法：按速度分成"**准静止** / **行驶中**"两套门限。行驶中要 4 项全过才施加观测：幅值 ✅、角速度 ✅、**平动加速度**（必须有效，且是这 4 项里**唯一与加计无关**的判据）✅、**方向散布放宽到 10°** ✅。
- 为什么方向散布必须放宽：3° 在行驶中几乎恒被撞穿，它反映的是**路面振动**；振动是随机的，窗口均值受影响远小于散布本身；
  而"系统性假重力"（恒定加/减速）交给平动加速度那一条挡。
- 安全性：行驶中 σ 从 1.5° 放宽到 3.0° ⇒ 单帧增益约 **2.7%**、时间常数约 4 s，相对 LiDAR 仍差 3 个数量级 ⇒ 只"慢拉"，不会突变。
- 新增参数（yaml）：`gravity_obs_motion_enable / motion_sigma_deg / motion_acc_dir_tol_deg / motion_min_speed_mps`；
  日志每帧打印 `模式 = 行驶中竖直锚/准静止/未施加` 和累计计数，验收时一眼能看出"到底有没有在拉"。

**② 冻结陀螺零偏的随机游走**（`fasterlio.b_gyr_cov: 5e-4 → 1e-8`）
- 证据：静止窗口测到的 `bg_z = −0.04157 rad/s = 2.39°/s`，方向正是 IMU 的 z 轴（本平台 IMU z = 车体前进方向 = **roll 轴**），
  而 LIO 的 roll 在同一段从 0 漂到 +18.97°，速率与它**完全同量级** ⇒ 现象就是"零偏被重新注入姿态"。
- 改法：把随机游走噪声降到极小 ⇒ 等价于"**锁定启动静止窗口测出来的那个零偏**"；
  同时 LIO 状态日志补打 `bg`，可以直接核对"全程是否基本恒定"。
- 回退条件：换 IMU / 换温度环境，或长时间（>10 min）出现**固定方向**的姿态漂移时，可调回 `1e-7 ~ 1e-6`。

**③ 外参里"单元内部竖直方向"重标定**（`fasterlio.extrinsic_R`）
- 证据（都不需要外参）：全 bag 16484 个地面点在**雷达系**里的法向与 **+y** 只差 **0.24~0.40°**（说明"雷达 +y 就是竖直向上"）；
  IMU 静止窗口 118 个样本的平均比力方向与"IMU −x"差 **11.3356°**（不是 0）。
- 结论：旧 `extrinsic_R` 声称"雷达 +y → IMU −x"，与实物差 **11.33°** ⇒ 雷达看到的地面在世界系里就是斜的 ⇒ 理论 z 漂移 **tan(11.33°) = 0.20 m/m**。

### 3.4 改外参踩的坑：手写小数让旋转矩阵"不正交"，程序启动即崩（下午）

> 这一条是**把上面 §3.3③ 的改动真跑起来才暴露的**，很值得单独记一笔：**改配置也能让程序起不来**。

**现象**：启动直接中止（SIGABRT），日志只有 15 行，停在 `slam with 3D UI` 之后，报
`Sophus ensure failed ... R is not orthogonal`。

**大白话根因**：新 `extrinsic_R` 是从计算结果里**四舍五入到 8 位小数**写进 yaml 的 ⇒ 它就**必然不是严格正交的**（实测误差 7e-9）；
而这款数学库构造旋转矩阵时会做正交性检查，误差超过它的极小阈值就**直接 abort**。
旧值是 `[0,-1,0; 1,0,0; 0,0,1]`（全是 0/±1，精确正交），所以这个坑一直没被发现。

**怎么定位的（决定性隔离实验）**：同一份程序、同一条 bag，**只把 yaml 里的外参换回旧值** ⇒ 报错 0 次、整条 bag 正常跑完
⇒ 坐实问题就是"新外参没正交化"，跟新加的"竖直锚/自检/冻结 bg"逻辑无关。

**改了什么**：新增 `math::OrthonormalizeRotation()`（用四元数归一化把矩阵投影到**最近的合法旋转矩阵**，误差 ~1e-16；
如果输入本来就够正交就**原样返回**，所以老配置行为零变化），并在**所有读 yaml 外参的入口**统一调用
（LIO 读外参处还会在残差偏大时打 WARNING）。

**三条经验**：① **手写旋转矩阵进配置，代码必须正交化**，不能指望"看着是整数就没事"；
② 改外参这种"只改数值"的改动也要**真跑一遍**，否则到车上就是"启动即崩"；
③ 报错里 `R is not orthogonal` 后面那 9 个数是 **R·Rᵀ**，不是 R 本身，别被它误导。

**大白话根因**（一行代码写错，效果却是"往自己正在遍历的数组里塞东西"）：

### 4.3 ★本次：实机定位"卡住 / 不丝滑"——刷 `当前DR定位的结果的时间戳应当比上一个时间戳数值大`（2026-10-09）

**现象 / 为什么要改**：车上用 `ros2 run lightning run_loc_online --config /home/h/ddh/code/ws/lightning_ws/src/lightning-slam/config/gaoda.yaml`
定位时，日志**经常**打印

```
WARNING: 当前DR定位的结果的时间戳应当比上一个时间戳数值大，实际相减得-0.0xx
```

每打印一次，定位就**卡一下**（车在动，但输出的位姿 / RViz / 下游 TF 停着不动），
跑起来"一顿一顿"、不够丝滑。

**大白话根因**：DR（惯导递推）那一路的时间戳**不是 IMU 的真实采样时标**。

- `ESKF::Predict()` 内部只做 `x_.timestamp_ += dt`（增量时间），它默认"当前时间"就是上次给的基准；
- `ProcessIMU()` 传进去的 `dt = 本帧 IMU 时标 − 上一帧 IMU 时标`（IMU 时间轴上的增量）；
- 但每处理完一帧激光，`Run()` 末尾都会执行 `kf_imu_ = kf_`，**把状态的"时间"重置成雷达帧末 `pcl_end_time`**
  ⇒ 基准和增量不是同一把"尺子"，DR 时间戳就整体错开一个偏移
  Δ = 最新 IMU 时标 − 雷达帧末（Δ 与处理延迟有关，实机上几十毫秒量级）。

偏移一旦超过"一帧 IMU 的时间"，新到的 DR 帧时间戳就比上一帧**更小** ⇒
`PGO::ProcessDR()` 判定"时间戳回退"，为了保住队列单调（`PoseInterp` / 外推都依赖它）直接 `return false` 丢掉该帧；
而**丢帧之后就不会调用 `PubResult()`** —— 高频定位输出（`high_freq_output_func_`）正是靠它驱动的。
更糟的是后续帧都带同一个偏移，会**连续丢**，直到 Δ 被时间追平 ⇒ 表现就是
"报一行警告 → 定位卡一阵"。

顺带两个后果：① `ExtrapolateLocResult()` 用 `dr_pose_queue_.back().timestamp_` 决定外推到哪个时刻，
时间轴错位 ⇒ 外推时刻算错、位姿抖动（"不丝滑"）；② 下游 `LocSystem::PublishTf()` 用定位结果的时间戳去查
`odom→base_link`，时标偏了会影响 TF 合成（`doc/modification_log.md` §2.6）。

**改了什么**

| 文件 | 改动（人话） |
| --- | --- |
| `src/core/lio/laser_mapping.cc` | `ProcessIMU()`：每次预测后把 DR 状态时间**显式对齐到当前 IMU 时标**（`kf_imu_.SetTime(timestamp)`），并且只在 `dt > 0` 时才预测（不再用负 `dt` 把状态"倒推"）。`Run()` 里重放 `imu_buffer_` 的循环：基准改成**状态自身时间**（原来取 `measures_.imu_.back()`，会让第一个 `dt` 偏大、把时间轴带偏），结束时同样对齐到最新一帧 IMU 时标 |
| `src/core/localization/pose_graph/pgo.cc` | `ProcessDR()`：回退帧**分两种情况**处理 —— 小幅回退（驱动抖动 / 重复帧）仍然丢帧，但警告改成限频（`LOG_EVERY_N(WARNING, 20)`，并打印累计次数）；**大幅回退**（> `pgo::PGO_DR_CLOCK_RESET_THD`）判定为 IMU / 驱动时钟复位，**清空 DR 队列后重新接入**，避免"永久丢新数据 ⇒ 定位彻底停更" |
| `src/core/localization/lidar_loc/lidar_loc.cc` | `ProcessDR()`：同一套策略（该队列也会被 `PoseInterp` 使用，必须严格单调） |
| `src/common/options.h` | 新增阈值 `pgo::PGO_DR_CLOCK_RESET_THD = 0.5`（s） |

**怎么验证的**：

1. 本机（x86）全量编译通过：`cd /home/h/ddh/code/ws/lightning_ws && colcon build --packages-select lightning`；
2. 代码逻辑核对：`ProcessDR` 的两条分支（丢帧 / 清队列重接）、`ProcessIMU` 与 `Run()` 两处时间对齐。

> 实机验收（需要上车跑一次，本机没有该车数据通路）：
> ① 正常情况：`run_loc_online` 不再刷那行 WARNING，车动起来连续、不卡顿；
> ② 若仍偶发：看新日志里的数值 —— **几毫秒级** = IMU 驱动本身的时标抖动/重复（查 RoboSense 驱动的
> `use_lidar_clock` / 时间同步设置）；出现 `DR时间戳大幅回退 … 判定为IMU/时钟复位` 的 ERROR = 驱动重连或设备时钟复位，
> 此时定位会自动恢复（不会再"卡死"）。

**影响 / 注意**：

- **不用重建地图**：只改 DR 的"时间戳语义"和"丢帧策略"，没动外参、世界系、地图基准；
- 需**重新编译**（含交叉编译到 Jetson）并替换车上的可执行文件；
