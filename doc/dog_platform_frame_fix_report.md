## 2. 三条相互独立的证据（都指向"差 180°"）——**✗ 三条都是错的**（见 §0）

> 三条都犯了同一个错误：拿【雷达系】的量（地面法向 `n`、车体"上"在雷达系 `up_laser`）**直接**和
> 【IMU 系】的加计静止均值 `â` 比角度，中间缺一次 `extrinsic_R` 换算。乘上 `extrinsic_R` 再比，
> 三者只差 **0.77°**（⇒ `â` 就是物理"上"⇒ 加计是标准约定）。本节保留原文以便对照教训。

**证据①（外参自检，程序自己报的）** 修复前日志原话：

```
【外参 up 方向自检(路面法向参照)】不一致：fasterlio.extrinsic_R 把雷达系路面法向
  0.0437472 0.982967 0.178499 映射到 IMU 的 -0.982967 -0.0437472 -0.178499，
而 IMU 静止窗口实测竖直 = 0.661488 0.6633 0.349951，相差 137.877 deg
```

注意这行里的两个"竖直"：**yaml 说的 up** `(-0.9830,-0.0437,-0.1785)` 与 **加计实测的 up** `(0.6615,0.6633,0.3500)`
几乎反向 —— 但两者又都不是"真值"，所以自检给出的 137.9° 只是"两者之差"，不是全部误差。

**证据②（bag 的 `/tf_static`，独立于 URDF 文本和程序）**

从 bag 里直接读 `/tf_static` 并把链串起来：`base_link → rslidartmp1 → laser_points_front`
（URDF 里写的安装角 Ry110°、Rz−45°），得到

```
T_base_laser : t = [0.4765, 0.0000, -0.0282] m
车体"上"在雷达系 : up_laser = R_base_laserᵀ · ẑ = [-0.6645, -0.6645, -0.3420]
bag 前 233 帧加计静止均值 : â = [0.6604, 0.6624, 0.3494]   (|â| = 0.9985 g)
```

⇒ **`angle(up_laser, â) = 179.51°`**：这台车的加计**比力方向朝下**（正常朝上）⇒ 必须给符号取反；
同时 yaml 里原写的 up（`-0.983,-0.044,-0.178`）离这个真值还差 **41.96°** ⇒ yaml 的 `ground_normal_lidar` 也是错的。

**证据③（落地面 RANSAC 拟合点云）** 起点周围 3 m 拟合地面：法向与竖直差 **0.75°**（地面是平的），
地面在起点传感器下方 **0.503 m** ⇒ 地面确实是"水平面"，反过来说明"车体被装反"的不是地面、而是车体系。

## 3. 结论表（修前 → 修后）——**✗ "修后"那列是第 6 次修复的值，其中外参/符号已被回退（见 §0）**

> 表里的**测量数字**（`R_vehicle_imu` 三行、自检角度、heading、离地高、点数）都是当时真实的日志/点云读数，
> 但**"修后"这一列所依据的两处配置改动是错的**（`extrinsic_R = I`、`imu_acc_up_sign = -1`）：
> 其中 `R_vehicle_imu`、heading、离地高等"看着修好了"，是因为错误的两处在这些量上互相抵消；

> 三点解读（**已按 §0 更正**）：
> 1. **真正的诊断**：修前那份 **车辆系偏航 180°**（`forward_axis: z` 让"车头"指反了；z 朝上是对的）；
>    第 6 次修复把 yaw 修对了（+46.2° ≈ 现在的 +44.3°）但**把 z 翻成了朝下**（车体系倒扣）；
>    第 7 次修复（z 朝上 + 车头 = IMU 的 −z）**两者都对**。
>    （表里那两行 179.51°/0.49° 都是**跨坐标系**比出来的数：前者拿雷达系 `up_laser` 直接比 IMU 系 `â`；
>    后者同理，只因 `â` 恰好垂直于那次旋转的轴 ⇒ 数值巧合，不能当"修好了"的判据。）
> 2. **点云那张图其实变了**：两个 180° 是"在宏观量上"抵消（离地高、地面倾角、z 范围都一样），
>    但**去畸变**用错了 `extrinsic_R` ⇒ 表面被抹开 = **重影**（厚度中位 115 mm vs 正确的 50.7 mm）。
>    这正是这个错误能藏住的原因：**只看这些宏观数、只看地图"像不像"都抓不到**，必须量重影。
> 3. **世界系没有翻**：那 180° 是**车辆系**（朝向显示）的差；实测两张地图（第 6 次修复前在线 vs 第 7 次修复后）
>    最近邻中位 **4 mm** ⇒ 一直在同一世界系里（所以"必须重建地图"不是因为基准变了，而是因为第 6 次修复后
>    那份图表面是重影的）。

## 4. 改了什么

| 文件 | 改动（人话） |
| --- | --- |
| `config/gaoda.yaml` | ① `fasterlio.extrinsic_R` → 单位阵（旧的两组错误值保留在注释里对照）**← ✗ 已回退成 `[0,-1,0, -1,0,0, 0,0,-1]`（见 §0）**；② `fasterlio.ground_normal_lidar` → 本平台实测 `[-0.6699,-0.6601,-0.3399]` **✓ 保留（第 6 次修复唯一该改的一项）**；③ 新增可选键 `fasterlio.imu_acc_up_sign: -1` **← ✗ 已改回 `+1`（缺省）** |
| `src/core/lio/imu_processing.hpp` | 新增成员 `acc_up_sign_`（**默认 +1 = 旧行为**，不影响别的平台）+ `SetAccUpSign()/GetAccUpSign()`；在 `IMUInit()`（静止均值 `mean_acc_`、逐帧 `cur_acc`）与 `UndistortPcl()`（去畸变用的比力）里统一乘该符号 |
| `src/core/lio/laser_mapping.{h,cc}` | 读 yaml 可选键（只接受 ±1，其它值告警并按 +1）→ `p_imu_->SetAccUpSign()`；`GetWindowImuMean()` 与**两处** `kf_imu_.Predict()` 用同一个 `GetAccUpSign()`；外参 up 自检判据分级（>3° 报"不一致"，0.4~3° 报"通过（小残差）"） |

改动站点（可 `grep -rn "个人修改（2026-10-09" src/` 逐条核对）：
`imu_processing.hpp:45/126/235/243/327/410`、`laser_mapping.cc:95/104/336/340/404/422/734/1083/1336`、
`laser_mapping.h:377`、`config/gaoda.yaml:205/251/265`。

**为什么加计符号要改 4 处（不能只改一处）**：世界系 z 是由"静止比力方向"定的。
`IMUInit()` 定世界系 z；`UndistortPcl()`、两处 `kf_imu_.Predict()` 都拿比力做预测项 `v̇ = R·f + g`；
`GetWindowImuMean()` 又拿比力做重力观测 —— 这几处**必须同号**，否则会出现"世界系朝上、预测项里重力却变成 -2g"
这种自相矛盾。现在全工程只有 `p_imu_->GetAccUpSign()` 一个取值点，以后要调只改一处。
**★ 这套"单点取号"的机制本次保留 ✓（代码一行未回退），只是号取 `+1`（= 缺省 = 第 6 次修复前的行为）**；
下面 §4 表里 `imu_processing.hpp` / `laser_mapping.{h,cc}` 两行的改动**都是保留项**（自检分级也是保留项）。
